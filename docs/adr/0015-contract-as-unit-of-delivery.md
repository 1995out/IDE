# ADR-0015: 合同是最小可验收交付单元；大需求按「项目 → 里程碑 → 合同 → 任务节点」分解

> **状态**: ACCEPTED（经 PR 审阅合入生效；合入前为提案，用户可在 PR 中否决）
> **日期**: 2026-10-30
> **决策依据**: 用户目标能力 `q18`「把一个无法掌握的大型 AI 软件项目，变成一组你能够理解、能够验收、能够追踪、能够维护的可控任务」（[`../scheme.md`](../scheme.md) §0）
> **相关**: ADR-0002（单工作区互斥）、ADR-0005（确定性验证）、ADR-0009（任务图点亮）、ADR-0014（两次点击）
> **权威正文**: [`../specs/project-decomposition.md`](../specs/project-decomposition.md)

## 背景

现有体系的全部机制都围绕**一份合同**：一份方案 → 一个 `ScopePlan` → 一份合同 → 一张任务图 → 一次合并。任务图节点从合同的写路径与验收条目生成（`src/lib/journey/proposal-from-contract.ts`）。

这对「改个按钮」足够，对「做一个系统」不够：

1. 合同预算默认 10 个文件、2000 行 diff、30 分钟（`src/lib/contract.schema.ts` `budget_limits` 默认值）。真实项目会远超一份合同。
2. 把大需求硬塞进一份合同，结果要么预算熔断，要么用户面对一次无法审阅、无法回滚的巨型合并。
3. 没有比合同更高的层级，用户无法回答「整个项目做到哪了、还剩什么」。

## 决策

1. **合同是最小可验收交付单元**。一份合同 = 一个用户能验收的结果 + 一组能自动判定的检查 + 一次可单独回滚的合并。合同的形状、签署、验证、合并规则一律不变。
2. **新增两层，放在合同之上**：
   - **项目计划（ProjectPlan）**：一个项目一份，由方案（`SchemeDraftV2`）分解得到，持久化在 `.stagent/project/plan.json`。
   - **里程碑（Milestone）**：一组有共同退出标准的合同；退出标准绑定方案的 `acceptance` 条目。
   任务节点仍在合同之下，规则不变（ADR-0009）。
3. **串行执行**。同一工作区一次只执行一份合同，这是 ADR-0002「单工作区互斥」在合同层的落实。现行代码只有 Daemon 进程锁，没有合同级互斥；TASK-L.9 在签署路径新增 `E_CONTRACT_IN_FLIGHT`。合同之间的顺序由计划里的依赖 DAG 决定。
4. **授权粒度不变**。每份合同仍有自己的「确认开工」与「合入」两次点击（ADR-0014 §2）。计划本身不是授权凭据：计划里没有的合同不能被签署；计划里有的合同，也必须单独签署。
5. **计划只经补丁演进**。分解、拆分、重排、删除都以计划补丁表达，经 Daemon 确定性校验后合并；被删除的合同进入墓地（INV-LEDGER-03 同款语义）。

## 后果

**正面**：
- 大需求变成一串小而可验收的合同，每份都能单独回滚。
- 项目进度有了唯一来源，画布能显示「项目地图」。
- 现有单合同机制零改动复用。

**代价**：
- 新增计划存储、计划补丁校验与分解步骤（TASK-L.7～L.10）。
- 跨合同的接口变更需要「接口先行」合同，顺序更长。
- 用户点击次数随合同数增加。缓解方式：每份合同的两次点击都在画布上一屏完成，不增加审阅负担（审阅后置仍有效）。

## 被否决的备选

- **一份大合同内多 Worker 并行**（RFC v0.2 §5）：与 ADR-0002 冲突，且失败时无法局部回滚。留在 RFC，v0.3+ 再议。
- **把里程碑做成合同状态机的一部分**：会让 9 态生命周期承担项目语义，破坏 ADR-0012 的单一终态。
