# ADR-0016: 目标项目的系统知识库随代码入库，每份合同同步维护

> **状态**: ACCEPTED（2026-10-30 用户原话 q22 明确授权通过）
> **日期**: 2026-10-30
> **决策依据**: 用户目标能力 `q18`、`q19`，用户授权拍板 `q22`（[`../scheme.md`](../scheme.md) §0）
> **相关**: ADR-0005（确定性验证）、ADR-0006（本地优先）、ADR-0015（合同为交付单元）
> **权威正文**: [`../specs/technical-design-and-knowledge.md`](../specs/technical-design-and-knowledge.md)

## 背景

Stagent 自己的仓库靠 `docs/`（ADR、规格、方案）保持可理解。但 Stagent **为用户造的项目**没有任何同类机制：

- 技术决策只存在于 Worker 的一次性输出里；
- `daemon/arch/*` 能现场算依赖图，但不落盘、不解释「为什么」；
- 方案快照存于 `.stagent/drafts/schemes/`，而 `.stagent/` 被写进 `.git/info/exclude`（`daemon/git/worktree-manager.ts`），换一台机器、换一个协作者就没了。

项目一旦长到几十份合同，用户就无法再回答「这个模块是干什么的」「当初为什么选这个库」「改这里会影响什么」。这正是 q19 要解决的失控点。

## 决策

1. **知识库放在目标项目仓库内**，默认路径 `docs/system/`（可在项目设置中改）。它随代码提交、随代码评审、随代码回滚。
2. **固定结构**：
   - `overview.md`：系统一页纸；
   - `modules.yaml`：模块地图，即模块 → 路径 → 职责 → 接口 → 来源合同；
   - `decisions/NNNN-*.md`：目标项目自己的 ADR；
   - `interfaces/`：跨模块接口登记；
   - `changelog.md`：每份合同一条，带合同号与方案条目号。

   字段定义见权威正文。
3. **维护是合同的一部分**。`ScopePlan` 在签署**前**把 `docs/system/**` 并入写范围（签署后不改合同）；Worker 交付时必须附带知识库增量。
4. **Daemon 确定性校验**，不靠模型自觉。校验以 `stagent check knowledge` 真实子进程运行，由退出码给出结论（ADR-0005 决策 1）：
   - 本次改动的每个文件都能被 `modules.yaml` 的某个模块路径覆盖；
   - 新增依赖必须有对应决策记录；
   - `changelog.md` 有本合同条目。

   不满足时证据记为 `FAILED`，原因码为 `KNOWLEDGE_DRIFT`。
5. **技术决策不再请用户拍板**，除非它属于「不可逆、花钱、碰安全、碰外部服务、删数据」五类（见权威正文 §3）。其余决策由设计步骤做出、写进 `decisions/`，用户随时可读、可推翻。

## 后果

**正面**：
- 系统描述与代码同生命周期，不会「文档在一边、代码在另一边」。
- 用户掌握系统靠读 `overview.md` 与模块地图，不靠记忆。
- 「为什么有这段代码」可以从提交 Trailer 反查到合同、方案条目、原话。

**代价**：
- 每份合同多一份产出与一道检查。
- 老项目需要一次引导（从目录结构与依赖图起草 `modules.yaml`）。
- 用户仓库里多出一个 `docs/system/` 目录。用户可改路径，不能关闭（关闭等于放弃 q19）。

## 被否决的备选

- **知识库放 `.stagent/`**：不入库，换机即丢，不随代码评审。
- **只靠现场分析（依赖图 + 模型总结）**：无法记录「为什么」，且每次结果可能不同，不满足可追踪。
