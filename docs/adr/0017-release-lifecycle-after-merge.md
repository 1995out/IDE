# ADR-0017: 发布（Release）是合并之后的独立生命周期；合同终态仍是 `MERGED`

> **状态**: ACCEPTED（经 PR 审阅合入生效；合入前为提案，用户可在 PR 中否决）
> **日期**: 2026-10-30
> **决策依据**: 用户目标能力 `q17`「需求理解、技术方案、功能实现、测试和部署这些环节串起来」（[`../scheme.md`](../scheme.md) §0）
> **相关**: ADR-0006（本地优先）、ADR-0012（`MERGED` 唯一终态）、ADR-0014 §3（凭据保险库）
> **权威正文**: [`../specs/release-and-operations.md`](../specs/release-and-operations.md)

## 背景

全库没有任何部署代码（deploy / release / health_check / vault 均为 0 命中）。合并进本地主分支就是终点，软件到不了能用的环境，「部署」这一环完全空白。

要补这一环，有两种放法：塞进合同状态机，或者单独一条生命周期。

## 决策

1. **Release 是独立生命周期**，状态为：
   - 主路径：`RELEASE_DRAFT → BUILDING → DEPLOYING → CHECKING_HEALTH → LIVE`
   - 异常终态：`FAILED`、`ROLLED_BACK`
   - 维护态：`SUPERSEDED`（被更新的 LIVE 取代）
2. **一次发布引用一个已合并的提交**，因而可以包含多份合同。合同终态仍是 `MERGED`（ADR-0012 不变）；发布失败不会解开任何已合并的合同。
3. **部署目标经适配器接入**。首版只做两类：
   - `local_process`：在本机拉起应用并保活；
   - `user_command`：执行仓库里用户自有的部署脚本，例如 `npm run deploy`。

   云平台适配器留到 v0.3+。
4. **配置与密钥只经凭据保险库注入**（ADR-0014 §3），且只注入部署与健康检查两步；安装与构建运行的是 Worker 写过的脚本，不注入密钥。仓库只保留 `.env.example` 声明变量名。真实值不进模型上下文、不进合同、不进日志。
5. **「发布」是一次显式点击**。它是对外、可能不可逆的动作，与合同的两次点击分开计数。探活失败时自动回滚到上一个 LIVE。手动「回滚」按钮在 `LIVE` 和 `FAILED` 卡上都可用，它等于以上一个 LIVE 的提交新建一次发布，不新增状态迁移。
6. **本地优先不变**：Stagent 不托管任何服务，只部署到用户自己拥有并提供凭据的目标（ADR-0006）。

## 后果

**正面**：
- 「部署」一环有了状态、证据、回滚。
- 合同机制零改动。
- 部署失败可以单独重试或回滚，不影响代码历史。

**代价**：
- 新增 Release 存储、状态机、两个目标适配器、健康检查与保险库（TASK-L.14、L.15）。
- 用户自有部署脚本的安全边界依赖命令白名单与环境注入规则，仍不是对抗性沙箱（ADR-0003）。

## 被否决的备选

- **合同状态机在 `MERGED` 后加 `DEPLOYED`**：违反 ADR-0012；一次部署常含多份合同，回滚语义会错位。
- **把部署交给 Worker 现场写脚本并执行**：Worker 无审批权、无外网，且部署是对外动作，必须由 Daemon 执行、用户点击。
