## 1. 产品边界待决（本文件不是已批准的部署承诺）

用户把“需求、方案、实现、测试和部署串起来”作为产品使命；但现有文档以本地代码合并为终点，没有裁定 Stagent 是否还要负责应用发布部署。本文件只列出需要产品决策和后续规格覆盖的问题，不承诺自动云部署、Docker、特定托管商或自动回滚。

---

## 2. 若纳入产品范围，需定义的生命周期问题

在新增部署能力前，需回答并确权：

- Stagent 的责任终点是验证后 Git 合并、生成可发布构建产物，还是把应用发布到目标环境？
- 目标用户自管环境，还是 Stagent 管理环境？首版支持哪些平台和运行时？
- 数据库迁移、Secrets 授权、DNS/域名、回滚及运行监控由谁负责？
- 哪些操作需要额外授权？部署证据怎样与 Contract、commit、Evidence 绑定？
- 不支持某类项目/平台时，如何清晰告知和交还给用户？

### 2.1 Secrets 安全约束（仅原则，不指定 Vault 实现）
1. **严禁明文进代码**：任何敏感配置（API Keys、数据库连接串、私钥）严禁通过 LLM 对话或 Git 提交传递；
2. **凭据安全绑定（Credential Vault 映射）**：
   - 项目根目录仅保留 `.env.example` 声明配置 Schema；
   - 部署执行器从宿主 Daemon 的安全 Vault 中以环境变量形式注入真实运行时凭据；
   - 部署日志中自动掩码所有匹配敏感正则的字符串（Masking）。

### 2.2 待选架构方向（需另立 ADR）

可考虑目标适配器、构建产物发布或用户手动部署等不同边界；当前没有批准的平台、接口或责任模型。任何具体接口应待产品边界与安全需求确认后再写入规范。

### 2.3 回滚与运行期责任待定义
若 Stagent 被授权承担部署责任，需定义健康检查、失败归因与回滚责任；重试次数、超时、自动回滚策略均需按目标平台与数据迁移风险另行决策，不在此处预设。
